Pagination lets you retrieve large query results in manageable chunks using the [Run APL query to edge deployment](/restapi/endpoints/queryEdge) endpoint (`POST https://AXIOM_DOMAIN/v1/query/_apl`).

<Note>
Use the edge query endpoint (`POST /v1/query/_apl`) for all new and existing pagination workflows. The legacy [Run APL query](/restapi/endpoints/queryApl) endpoint (`POST /v1/datasets/_apl`) is deprecated and reaches end of life on December 31, 2026. The legacy [Run query](/restapi/endpoints/queryDataset) endpoint (`POST /v1/datasets/{dataset_name}/query`) reached end of life on October 31, 2026.
</Note>

## Pagination mechanisms

Choose one of the following pagination mechanisms:

- [Timestamp-based pagination](#timestamp-based-pagination) (recommended, stable)
- [Cursor-based pagination](#cursor-based-pagination) (public preview)

Axiom recommends timestamp-based pagination. Cursor-based pagination is in public preview and only supports a subset of APL queries.

## Timestamp-based pagination

To paginate results by timestamp with `POST /v1/query/_apl`:

1. Include the [`limit` operator](/apl/tabular-operators/limit-operator) in the APL query to set the number of events per page. Without a `limit` operator, Axiom defaults to 1,000 rows per page.
1. Include `sort by _time desc` or `sort by _time asc` in the APL query to return results in descending or ascending chronological order. For more information, see the [`sort` operator](/apl/tabular-operators/sort-operator).
1. Specify `startTime` and `endTime` in the request body.

### Page through the result set

Use event timestamps as boundaries to fetch each subsequent page.

#### Queries in descending order

To fetch the next page when sorting by `_time desc`:

1. Find the `_time` value of the last event on the current page (the oldest event returned).
1. Optional: Subtract 1 nanosecond from that timestamp.
1. Send the next request with `endTime` set to that timestamp while keeping `startTime` unchanged.

Stop when a page is shorter than the requested page size. If the boundary stops advancing, see [Deduplication](#deduplication).

#### Queries in ascending order

To fetch the next page when sorting by `_time asc`:

1. Find the `_time` value of the last event on the current page (the newest event returned).
1. Optional: Add 1 nanosecond to that timestamp.
1. Send the next request with `startTime` set to that timestamp while keeping `endTime` unchanged.

Stop when a page is shorter than the requested page size. If the boundary stops advancing, see [Deduplication](#deduplication).

#### Deduplication

Adjusting the boundary timestamp by 1 nanosecond is optional:

- If you keep the exact timestamp, the boundary event (and any events sharing that timestamp) appears again on the next page.
- If you add or subtract 1 nanosecond, you skip any additional events that share the exact same nanosecond timestamp.

Deduplicate repeated events in your client. If a full page shares one timestamp, a timestamp alone cannot distinguish the remaining events. Use cursor-based pagination for supported queries when you need to retrieve every event at that timestamp.

### Examples

#### Initial request

```bash
curl -X 'POST' 'https://AXIOM_DOMAIN/v1/query/_apl?format=tabular' \
  -H 'Authorization: Bearer API_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{
    "apl": "DATASET_NAME | sort by _time desc | limit 100",
    "startTime": "2026-11-01T00:00:00.000Z",
    "endTime": "2026-11-01T23:59:59.999Z"
  }'
```

## Cursor-based pagination

Cursor-based pagination is in public preview. Axiom recommends timestamp-based pagination for production workloads.

### Requirements

Cursor-based pagination only supports plain, non-aggregated APL queries on a dataset with a single sort by `_time`:

- Include the [`limit` operator](/apl/tabular-operators/limit-operator) in the APL query to set the page size.
- Sort only by `_time` using `sort by _time desc` or `sort by _time asc`.
- Do not include aggregations or grouping (such as `summarize`). Queries with aggregations or a sort on any field other than `_time` return an error when a `cursor` is supplied.
- Specify `startTime` and `endTime` in the request body and keep them unchanged across subsequent pages.

### Request parameters

Add these fields to the JSON request body of `POST /v1/query/_apl`:

<ParamField body="cursor" type="string">
  Optional. Cursor string from the previous response (`status.minCursor` for descending queries or `status.maxCursor` for ascending queries) to fetch the next page.
</ParamField>

<ParamField body="includeCursor" type="boolean" default="false">
  Optional. Controls whether the boundary row matching `cursor` is included in the returned page. Set to `true` to include the boundary row; omit or set to `false` to exclude the boundary row and avoid repeating it.
</ParamField>

### Response fields

With `format=tabular`, the response contains pagination metadata in `status` and result rows in `tables`:

<ResponseField name="status" type="object">
  Metadata about the query execution, including cursor boundaries.
</ResponseField>

<ResponseField name="status.minCursor" type="string">
  Cursor for the earliest (oldest) event in the current page.
</ResponseField>

<ResponseField name="status.maxCursor" type="string">
  Cursor for the latest (newest) event in the current page.
</ResponseField>

<ResponseField name="status.rowsMatched" type="integer">
  Total number of rows matching the query.
</ResponseField>

<ResponseField name="tables" type="array">
  Tabular result sets containing `fields` and `columns`. If you request `format=legacy`, events are returned in `matches` instead.
</ResponseField>

### Page through the result set

Keep `startTime`, `endTime`, and the APL query identical across requests, and update `cursor` on each page:

- **Descending order (`sort by _time desc`):** Pass `status.minCursor` from the previous response as `cursor` in the next request. Stop when a page returns fewer rows than your `limit`, or when `status.minCursor` matches the `cursor` you sent.
- **Ascending order (`sort by _time asc`):** Pass `status.maxCursor` from the previous response as `cursor` in the next request. Stop when a page returns fewer rows than your `limit`, or when `status.maxCursor` matches the `cursor` you sent.

### Examples

#### Initial request

```bash
curl -X 'POST' 'https://AXIOM_DOMAIN/v1/query/_apl?format=tabular' \
  -H 'Authorization: Bearer API_TOKEN' \
  -H 'Content-Type: application/json' \
  -d '{
    "apl": "DATASET_NAME | sort by _time desc | limit 100",
    "startTime": "2026-11-01T00:00:00.000Z",
    "endTime": "2026-11-01T23:59:59.999Z"
  }'
```
