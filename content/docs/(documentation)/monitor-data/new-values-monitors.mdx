New values monitors alert you when a column of your query results holds a value that Axiom hasn’t seen in that column recently. Use them when the first appearance of something is worth knowing about. For example:

- **Reliability:** A new error message in your service after a deploy, or a new exception type in a background job.
- **Security:** A new IP address on your network, a new country that a user signs in from, or a new AWS API call in your audit logs.
- **Infrastructure:** A new host, container image, or service version that starts sending data, or a new domain that your workloads resolve.
- **Product:** A new customer that calls your API, a new client version in the user agents of your requests, or a new tool that your AI agent uses.

Each time the monitor runs, Axiom compares the values of the watched column in the query results with the values that the monitor recorded during the lookback period. Axiom sends a notification for each value that it hasn’t seen in this period, and then records the value so that it doesn’t alert on it again until the lookback period has passed without the value appearing.

## Create new values monitor

To create a new values monitor, follow these steps:

1. Click the **Monitors** tab, and then click **New monitor**.
1. Click **New values**.
1. Name your monitor and add a description.
1. Write an Axiom Processing Language (APL) query whose results contain the column you want to watch, and then click **Run query** to preview the results. For example, the following query returns the error messages of a service:

    ```kusto
    ['my-logs']
    | where level == 'error'
    | project message
    ```

    The query can filter, transform, and aggregate events. For more information, see [Introduction to APL](/apl/introduction).
1. In the preview, select the checkbox in the header of the column you want to watch. You can watch one column. You can’t watch `_time` or the result of an aggregation, such as `count()`. If the results contain a single column that you can watch, Axiom selects it for you.
1. Configure the monitor using the following options:
    - **Run every** is how often the monitor runs. Each run checks the events since the previous run, so the monitor has no separate time range.
    - **Forget values after** is the lookback period in days. A value counts as new when the monitor hasn’t seen it in this many days. The default is 365 days.
    - **Learn from** is the number of previous days of events that the monitor records as already seen before it first runs. The possible values are 0, 1, 7, 14, and 30 days, and the value can’t exceed **Forget values after**. The default is 30 days. If your query aggregates, set this to 0 days. For more information, see [Learning period](#learning-period).
1. Click **Add notifier**, and then select the notifiers that define how you want to receive notifications for this monitor. For more information, see [Notifiers](/monitor-data/notifiers-overview).
1. Click **Create**.

You have created a new values monitor. Axiom alerts you each time the watched column holds a value that the monitor hasn’t seen during the lookback period.

<Info>
New values monitors only support APL queries on event datasets. They don’t support metrics datasets.
</Info>

## Learning period

When you create a new values monitor, Axiom records the values that the query returns over the learning period as already seen. This prevents the first runs of the monitor from alerting on values that already appear in your data.

If you set **Learn from** to 0 days, the monitor doesn’t look at past events. Instead, the first run that returns values records them without sending notifications, and the monitor only alerts on values that appear after this run. Values that appeared before the monitor was created but are rare, such as a weekly job, can trigger notifications when they next appear.

### Queries that aggregate

If your query aggregates, for example with `summarize`, set **Learn from** to 0 days.

To record the values of the learning period, Axiom runs your query once over the whole period. Each later run of the monitor only covers the events since the previous run. An aggregation over the whole learning period returns different results from the same aggregation over a single run, so the recorded values don’t match the values that the monitor checks later. For example, the following query returns the clients that send at least 200 requests:

```kusto
['http-logs']
| summarize requests = count() by client
| where requests >= 200
```

Over a learning period of 30 days, a client that sends a few requests each day reaches 200 requests, and the monitor records it as already seen. The monitor then doesn’t alert on this client when it first sends 200 requests within a single run.

## Notifications

A new values monitor sends one notification for each new value. Each notification contains the new value. Notifications sent to [custom webhook notifiers](/monitor-data/custom-webhook-notifier) also contain one row of the query results that holds the new value, in `.MatchedEvent`.

A run sends at most 9 notifications. If a run finds more new values, the monitor doesn’t record the ones it didn’t send notifications for, so they trigger a notification the next time they appear.

A new values monitor doesn’t resolve. It doesn’t send a notification when a value stops appearing.

## Limits

- Within the lookback period, the watched column can hold fewer than 50,000 distinct values.
- A single run can find at most 1,000 new values.

If a monitor exceeds a limit, its runs fail. To stay within the limits, watch a column with fewer distinct values, filter your query, or shorten the lookback period. For example, watch an error message after removing the IDs and numbers it contains, rather than the raw message.

## Data that arrives late

Each run of a new values monitor only checks the events whose `_time` falls between the previous run and the current run. If an event arrives in Axiom after the run that covers its `_time`, no run checks it, and the monitor doesn’t alert on its value.

If your data can arrive late, set `secondDelay` when you create or update the monitor using the [API](/restapi/endpoints/createMonitor). This shifts the time range of each run into the past by the number of seconds you specify. For example, with a delay of 900 seconds, a run at 10:15 checks the events up to 10:00.
