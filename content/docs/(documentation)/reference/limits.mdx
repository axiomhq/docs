Axiom applies certain limits and requirements to guarantee good service across the platform. Some of these limits depend on your pricing plan, and some of them are applied system-wide. This reference article explains all limits and requirements applied by Axiom.

Limits are necessary to prevent potential issues that could arise from the ingestion of excessively large events or data structures that are too complex. Limits help maintain system performance, allow for effective data processing, and manage resources effectively.

### Restrictions on datasets and fields

Axiom restricts the number of datasets and the number of fields in your datasets. The number of datasets and fields you can use is based on your pricing plan and explained in the table above.

If you ingest a new event that would exceed the allowed number of fields in a dataset, Axiom returns an error and rejects the event. To prevent this error, ensure that the number of fields in your events are within the allowed limits.

To reduce the number of fields in a dataset, use one of the following approaches:
- [Delete the fields](/reference/datasets#delete-fields) you don’t need.
- [Vacuum the fields](/reference/datasets#vacuum-fields) to remove fields that no longer occur in events within your retention period. If necessary, [trim the dataset](/reference/datasets#trim-dataset) first.
- Use [map fields](/apl/data-types/map-fields).

To prevent new fields from being added to an event dataset, [lock its schema](/reference/datasets#lock-dataset-schema).

## System-wide limits

The following limits are applied to all accounts, irrespective of the pricing plan.

### Limits on ingested data

The table below summarizes the limits Axiom applies to each data ingest. These limits are independent of your pricing plan. For metrics, see [Limits on ingested metrics](#limits-on-ingested-metrics).

|                              | Limit     |
| ---------------------------- | --------- |
| Maximum field size           | 1 MB      |
| Maximum events in a batch    | 10,000    |
| Maximum field name length    | 200 bytes |

If you try to ingest data that exceeds these limits, Axiom does the following:
- Replaces strings that are too long with `<invalid string: too long>`.
- Replaces binary with `<invalid data>`.
- Truncates maps and slices that nest deeper than 100 levels and replaces them with `nil` at the cut-off level.
- Converts the following float values to `nil`:
    - NaN
    - +Infty
    - -Infty

### Limits on ingested metrics

The limits below apply to OpenTelemetry metrics that you send to the `/v1/metrics` endpoint. They’re separate from the event ingest limits above and independent of your pricing plan.

|                                          | Limit                   |
| ---------------------------------------- | ----------------------- |
| Maximum request size                     | 4 MiB (4,194,304 bytes) |
| Maximum metric name length               | 256 bytes               |
| Maximum attribute name length            | 256 bytes               |
| Maximum attribute value length           | 1 KiB (1,024 bytes)     |
| Maximum buckets per histogram data point | 256                     |
| Maximum quantiles per summary data point | 256                     |

The maximum request size applies to the uncompressed payload. Axiom accepts gzip, zstd, brotli, and deflate compression, and compressing requests reduces the bandwidth you use. Axiom checks the request size after decompressing the request, so compression doesn’t allow you to send more data in a single request.

If a request exceeds the maximum request size, Axiom rejects it with the HTTP status code `413`. The OpenTelemetry Collector treats this status code as a permanent error, so it drops the batch instead of retrying it.

To keep requests within the limit, use the `batch` processor in your OpenTelemetry Collector configuration and set `send_batch_max_size`. Whether a given batch size stays within 4 MiB depends on the number of attributes that your data points carry. If you receive `413` responses, reduce `send_batch_max_size`. For an example configuration, see [Send OpenTelemetry data to Axiom](/send-data/opentelemetry).

The maximum number of buckets applies to each histogram data point and counts the entries in its `explicit_bounds` list. The implicit overflow bucket that catches values above the last boundary doesn’t count towards the limit. For summary data points, the limit counts the entries in the `quantile_values` list.

If a metric name, an attribute, or the number of buckets or quantiles exceeds the limits above, Axiom doesn’t reject the whole request. It rejects the affected data points, responds with the HTTP status code `200`, and returns an OpenTelemetry `partial_success` message that reports the number of rejected data points and the reason. For example, a histogram data point with too many buckets is reported as `[http.server.duration] metric limit violation: Bucket count 300 (explicit_bounds/quantile_values) exceeds limit 256`.

### Special fields

Axiom creates the following two fields automatically for a new dataset:

- `_time` is the timestamp of the event. If the data you ingest doesn’t have a `_time` field, Axiom assigns the time of the data ingest to the events. If you ingest data using the [Ingest data](/restapi/endpoints/ingestToDataset) API endpoint, you can specify the timestamp field with the [timestamp-field](/restapi/endpoints/ingestToDataset#parameter-timestamp-field) parameter.
- `_sysTime` is the time when you ingested the data.

In most cases, use `_time` to define the timestamp of events. In rare cases, if you experience clock skews on your event-producing systems, `_sysTime` can be useful.

### Reserved field names

Axiom reserves the following field names for internal use:

- `_blockInfo`
- `_cursor`
- `_rowID`
- `_source`
- `_sysTime`

Don’t ingest data that contains these fields names. If you try to ingest a field with a reserved name, Axiom renames the ingested field to `_user_FIELDNAME`. For example, if you try to ingest the field `_sysTime`, Axiom renames it to `_user_sysTime`.

In general, avoid ingesting field names that start with `_`.

### Requirements for timestamp field

The most important field requirement is about the timestamp.

<Note>
All events stored in Axiom must have a `_time` timestamp field. If the data you ingest doesn’t have a `_time` field, Axiom assigns the time of the data ingest to the events. To specify the timestamp yourself, include a `_time` field in the ingested data.
</Note>

If you include the `_time` field in the ingested data, follow these requirements:

- Timestamps are specified in the `_time` field.
- The `_time` field contains timestamps in a valid time format. Axiom accepts many date strings and timestamps without knowing the format in advance, including Unix Epoch, RFC3339, or ISO 8601.
- The `_time` field is a field with UTF-8 encoding.
- The `_time` field isn’t used for any other purpose.

### Requirements for log level fields

Axiom uses log levels to help you spot errors and warnings in Stream, query results, and trace logs. The event timeline groups events by the same levels. Axiom reads the level from your event’s fields; your stored data and monitor conditions stay unchanged.

For example, this event displays as `info`, even though its message contains the word `error`:

```json
{"level": "info", "message": "Recovered from a connection error"}
```

Axiom chooses the level in three steps:

1. Check supported fields in [priority order](/reference/limits#field-priority). Use the first recognized value.
2. If none supplies a level, look for a keyword at the start of the [message](/reference/limits#message-fallback).
3. If nothing matches, display `unknown` in a neutral color.

#### Inspect a log level

Hover over a severity marker to see the field and value behind it. In event details, click the level badge to highlight that field.

The tooltip links to the relevant documentation. **Text levels** means no single source format was identified; **Message** means the level came from a message keyword.

#### Field priority

Axiom checks the following fields from top to bottom, and from left to right within each row. It skips missing fields and unrecognized values. Once a value matches, later fields don’t affect the level.

| Priority | Fields | Values |
| --- | --- | --- |
| 1 | `_row_status` | Dashboard override using a [text level](/reference/limits#recognized-values). |
| 2 | `severity_id` with `class_uid` | [OCSF severity IDs](/reference/limits#supported-schemas). |
| 3 | `severity_text`, `severity_number`, `severityText`, `severityNumber` | [OpenTelemetry text or numeric levels](/reference/limits#supported-schemas). |
| 4 | `level`, `severity`, `log.level`, `@level`, `@severity` | Text levels. `severity` also accepts Syslog codes when the event has Syslog headers. |
| 5 | `record.level`, `record.severity` | Text levels. |
| 6 | `data.log_level` | Convex console log levels. |
| 7 | `record.error` | Text levels, such as `error`. Error descriptions and exception objects don’t match. |
| 8 | `log.syslog.severity.code`, `log.syslog.severity.name` | Syslog codes or names. |
| 9 | `type` and `record` fields | [AWS Lambda platform events](/reference/limits#aws-lambda-platform-events). |

<Accordion title="Nested fields and map fields">

Axiom reads both dotted field names and nested values. These events all supply `record.level`:

```json
{"record.level": "info"}
{"record": {"level": "info"}}
{"record": "{\"level\": \"info\"}"}
```

The same applies to deeper paths. For example, `log.syslog` can be a map containing `severity.code`.

If more than one representation exists, Axiom uses the longest column name with a non-null value before reading nested keys. For example, a `record.level` column takes priority over `level` inside a `record` map. To read a level from an array element, extract it with a [virtual field](/query-data/virtual-fields).

</Accordion>

#### Recognized values

Text values match exactly, ignoring capitalization. `ERROR` matches `error`; `errorful` and `error: request failed` don’t.

| Display level | Text values |
| --- | --- |
| `trace` | `trace` |
| `debug` | `debug` |
| `info` | `info` |
| `notice` | `notice` |
| `warn` | `warn`, `warning` |
| `error` | `err`, `error` |
| `critical` | `crit`, `critical` |
| `fatal` | `fatal` |
| `alert` | `alert` |
| `emergency` | `emerg`, `emergency` |
| `success` | `success` |
| `unknown` | `unknown` |

Levels keep their names even when they share a color. For example, `debug` and `info` are both blue, but appear separately in the event timeline.

#### Supported schemas

Axiom detects the format of each event from its fields. Numeric levels differ by format: `5` means `debug` in OpenTelemetry, `notice` in Syslog, and `critical` in OCSF.

<AccordionGroup>
<Accordion title="OpenTelemetry (OTel)">

Axiom recognizes `severity_text`, `severity_number`, `severityText`, and `severityNumber`. Text fields accept the [text levels above](/reference/limits#recognized-values), plus numbered names such as `WARN2` and `FATAL4`. Numeric fields use these ranges:

| Number | Display level |
| --- | --- |
| 1–4 | `trace` |
| 5–8 | `debug` |
| 9–12 | `info` |
| 13–16 | `warn` |
| 17–20 | `error` |
| 21–24 | `fatal` |

`0` means unspecified, so Axiom continues to the next field. For more information, see [OpenTelemetry severity fields](https://opentelemetry.io/docs/specs/otel/logs/data-model/#severity-fields).

</Accordion>
<Accordion title="AWS Lambda">

Lambda application logs use text levels such as `level` or `record.level`, followed by [message fallback](/reference/limits#message-fallback). Logs generated by the Lambda service use the [platform event rules below](/reference/limits#aws-lambda-platform-events).

Axiom identifies Lambda logs by `axiom.awsLambdaExtensionVersion`. For older extension versions, all five of these fields identify Lambda: `lambda.initializationType`, `lambda.region`, `lambda.name`, `lambda.memorySizeMB`, and `lambda.version`.

For more information, see [AWS Lambda log levels](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-cloudwatchlogs-log-level.html).

</Accordion>
<Accordion title="Convex">

Axiom reads Convex console log levels from `data.log_level`:

| Value | Display level |
| --- | --- |
| `DEBUG` | `debug` |
| `INFO`, `LOG` | `info` |
| `WARN` | `warn` |
| `ERROR` | `error` |

The `convex.deployment_name` field identifies the event as Convex; `data.log_level` still supplies a level without it.

The function execution status in `data.status` doesn’t set a console log level. Use that field directly in queries and monitors for function failures. For more information, see the [Convex log event schema](https://docs.convex.dev/production/integrations/log-streams#log-event-schema).

</Accordion>
<Accordion title="Open Cybersecurity Schema Framework (OCSF)">

Axiom reads `severity_id` when `class_uid` is a nonnegative integer, including `0`.

| ID | Display level |
| --- | --- |
| 0 | `unknown` |
| 1 | `informational` |
| 2 | `low` |
| 3 | `medium` |
| 4 | `high` |
| 5 | `critical` |
| 6 | `fatal` |
| 99 | The event’s `severity` text, converted to lowercase, or `other` if the text is empty or absent. |

For ID `99`, Axiom uses `other` if `severity` isn’t a string. For more information, see the severity attributes in the [OCSF schema](https://schema.ocsf.io/1.2.0/classes/authentication).

</Accordion>
<Accordion title="Syslog">

Axiom reads codes from `log.syslog.severity.code` and names from `log.syslog.severity.name`.

| Code | Display level |
| --- | --- |
| 0 | `emergency` |
| 1 | `alert` |
| 2 | `critical` |
| 3 | `error` |
| 4 | `warn` |
| 5 | `notice` |
| 6 | `info` |
| 7 | `debug` |

Names accept the [text levels above](/reference/limits#recognized-values), plus `informational` as `info`. A numeric string in the name field isn’t treated as a code.

Axiom also reads these codes and names from `severity` when `hostname`, `application`, and `message` are all strings. Empty strings count. Without those headers, a numeric `severity` value has no default meaning.

Axiom doesn’t read severity from the combined Syslog priority value (PRI) or from `event.severity`. For more information, see [Syslog severity levels](https://www.rfc-editor.org/rfc/rfc5424.html#section-6.2.1).

</Accordion>
</AccordionGroup>

Numeric fields accept numbers and their exact decimal strings. For example, `severity_number: 17` and `severity_number: "17"` both display as `error`. Values outside the supported ranges, leading zeros such as `"017"`, and text such as `"Severity(17)"` don’t match.

##### AWS Lambda platform events

Axiom uses these rules when earlier fields haven’t supplied a level. Event types include the `platform.` prefix, and their field values are case-sensitive. For example, `type: "platform.extension"` with `record.state: "Ready"` displays as `info`.

<Accordion title="Platform event levels">

| Event type | Condition | Display level |
| --- | --- | --- |
| `platform.start`, `platform.logsSubscription`, `platform.logSubscription`, `platform.telemetrySubscription` | Any | `info` |
| `platform.logsDropped` | Any | `warn` |
| `platform.fault` | Any | `error` |
| `platform.initStart`, `platform.restoreStart` | `record.runtimeVersion` is a nonempty string | `info` |
| `platform.initStart`, `platform.restoreStart` | `record.runtimeVersion` is missing or empty | `debug` |
| `platform.initRuntimeDone`, `platform.restoreRuntimeDone`, `platform.runtimeDone` | `record.status` is `success` | `debug` |
| `platform.report`, `platform.restoreReport` | `record.status` is `success` or absent | `info` |
| `platform.initReport` | `record.initializationType` is `on-demand` | `debug` |
| `platform.initReport` | `record.initializationType` is `provisioned-concurrency`, `snap-start`, or `lambda-managed-instances` | `info` |
| `platform.extension` | `record.state` is `Ready` | `info` |
| `platform.extension` | `record.state` is `InitError`, `ExitError`, `ShutdownFailed`, or `LaunchError` | `warn` |

For runtime and report events, `record.status` values of `failure`, `error`, and `timeout` produce `warn`. On `platform.initReport`, a failure status takes priority over the initialization type.

Other or malformed values produce `unknown`. For example, an unrecognized extension state stays neutral. A report without a status retains `info` for compatibility with older Lambda logs. A platform event that produces `unknown` doesn’t continue to message fallback.

</Accordion>

#### Message fallback

If no field supplies a level, Axiom checks the text in `message`, `msg`, `@message`, `text`, `record`, and `data.message`, in that order.

For each string, it reads at most the first 100 characters and the first two lines. The first complete [severity word](/reference/limits#recognized-values) determines the level, ignoring capitalization. The word `unknown` is excluded from this check.

For example:

| Event | Display level | Why |
| --- | --- | --- |
| `{"message": "WARN retry; error"}` | `warn` | `WARN` is the first keyword. |
| `{"message": "request started\nerror: connection refused\nretry scheduled"}` | `error` | `error` appears on the second line. |
| `{"message": "request started\nconnecting to database\nerror: connection refused"}` | `unknown` | `error` appears after the first two lines. |

If nothing matches, Axiom displays `unknown`.

#### Map a custom field

If your logs use another field name, create a [virtual field](/query-data/virtual-fields#creating-a-virtual-field) named `level` or `severity`. Return one of the recognized values from that field to use it for highlighting.

For example, if `app_log_level` contains `INFO` and `ERROR`, create a virtual field with the following settings:

- **Name:** `level`
- **Expression:** `tostring(app_log_level)`

Virtual fields follow the same [priority order](/reference/limits#field-priority) as stored fields.

## Temporary account-specific limits

If you send a large amount of data in a short amount of time and with a high frequency of API requests, Axiom may temporarily restrict or disable your ability to send data to Axiom. This is to prevent abuse of the platform and to guarantee consistent and high-quality service to all customers. In this case, Axiom kindly asks you to reconsider your approach to data collection. For example, to reduce the total number of API requests, try sending your data in larger batches. This adjustment both streamlines Axiom operations and improves the efficiency of your data ingest. If you often experience these temporary restrictions and have a good reason for changing these limits, please [contact Support](https://axiom.co/contact).
